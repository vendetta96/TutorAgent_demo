Tutor Bot — Technical Report

AI Engineer Assignment · a Pipecat + OpenAI voice agent that teaches a class about natural disasters

1. Overview

Tutor Bot is a real-time voice agent that presents an eight-slide lesson on natural disasters to school students (ages ~10–14), answers their questions mid-lesson, returns to the slides, and finishes with a two-way Q&A. The starting point was a prototype whose slide progression depended on silence timers and whose behaviour was unpredictable. The submission rebuilds the agent around a small, framework-free state machine, keeps every piece of business logic unit-testable without a network, and uses Pipecat as the only framework and OpenAI as the only external service.

2. Architecture

2.1 Pipeline

Green boxes are components written for this submission; the rest are Pipecat/OpenAI services. Observers see every frame without being in the audio path, which is where the slide-progression logic lives.

2.2 Key components

ComponentResponsibility
tutor/controller.py
PresentationController		Pure state machine: modes IDLE → PRESENTING → QNA → ENDED, current slide, paused flag, whether the student interrupted mid-slide, statistics. It receives events (bot started/stopped speaking, user started/stopped, advance, pause, stall, idle) and returns Actions (present slide, continue slide, enter Q&A, idle prompt, end session, schedule advance). No timers, no I/O, no Pipecat imports.
tutor/processors/presentation_driver.py
PresentationDriver (observer)		Executes the controller's actions inside Pipecat: injects slide prompts via LLMMessagesAppendFrame(run_llm=True), runs the 1.2 s slide gap, an 8 s stall watchdog, the Q&A idle timer, pause/resume, graceful end (stop_when_done), and broadcasts state to the UI. It guards the advance with an "LLM busy / tool call pending" check so a slow generation or a tool round-trip never causes a premature slide change.
tutor/prompts.pySystem prompt, per-slide messages, Q&A / idle / goodbye messages, and build_state_note() — the [PRESENTER STATE] note refreshed before every inference.
tutor/processors/context_augmenter.pySits between the user aggregator and the LLM. On every LLMContextFrame it replaces the previous state note with a fresh one and, when the trigger is a student utterance, embeds it and appends the top-3 knowledge passages.
tutor/tools.pyLLM tools go_to_slide(slide_number | topic), next_slide(), end_session(). Handlers update the controller and return the slide content as the tool result, so the LLM continues presenting in the same turn.
tutor/processors/pause_gate.pyFrame processor between TTS and the output transport. While paused it holds every downstream data/control frame (audio, text, TTS start/stop, LLM response end) in order; on resume it releases them. System frames and upstream frames pass through so the pipeline stays healthy.
tutor/safety.py + processors/safety_processor.pyDeterministic guard (regex rules per category + PII detectors) applied to each transcription before it reaches the aggregator. Blocked text is dropped; a fixed spoken reply is emitted via TTSSpeakFrame; a one-line system note keeps the LLM context coherent. Optional OpenAI moderation layer. PausedUserMuteStrategy suppresses VAD/interruptions/transcriptions while paused.
tutor/knowledge/Markdown chunker (by heading, paragraph-packed, content-hash ids), numpy cosine VectorStore with JSON persistence, incremental ingest_documents(), OpenAI embedder, CLI.
tutor/metrics.py + processors/metrics_observer.pyCollector fed by Pipecat MetricsFrames (TTFB, processing, LLM tokens, TTS characters, STT seconds) plus our own signals (user→bot response latency, tool calls, pauses, safety blocks). Renders the console report on disconnect; GET /report/latest serves it to the UI.
tutor/transcripts.py + tutor/improve/JSONL session recorder (PII-redacted) and the offline improvement loop (analyzer + LLM judge + FAQ/guidance generation).
frontend/app.tsConnect / Pause / Resume / Disconnect; renders server-pushed lesson state; suspends the WebAudio AudioContext on pause for instant, sample-exact resume; shows the metrics report after disconnect.

2.3 Important technical decisions

  • Deterministic slide progression, not LLM-driven. Each slide is one LLM turn. When the bot finishes speaking and 1.2 s of silence passes (and no LLM response or tool call is in flight), the controller advances. The LLM only ever receives the content of the current slide, so it cannot run ahead, and the end of the deck is a state-machine transition rather than a hope that the model calls a function. Tools exist for student-requested navigation only.
  • Per-inference state note. Rather than trying to inject a message at exactly the right moment after an interruption (racy), a small note describing the exact situation is rewritten before every LLM call. Pipecat's assistant aggregator commits only the text that was actually spoken before an interruption, so "continue from where you stopped" is grounded in the real context.
  • Hybrid pause. The WebSocket transport sends audio at 2× real time, so a server-only gate would leave seconds of audio already buffered in the browser. The server gate is the authority (and is unit-tested); the browser's AudioContext.suspend() makes the pause instant and the resume sample-exact.
  • Rules first, model second, for safety. Regex rules are exact, explainable and testable, so they form the first layer; the system prompt handles paraphrases; the moderation endpoint is available as a third layer. Blocked content never reaches the LLM.
  • Framework-free core. Everything in tutor/ except processors/ and tools.py has no Pipecat dependency, which is what makes 115 fast deterministic tests possible. A separate wiring test constructs the real pipeline and asserts the processor order and tool registration.
  • Recovery paths. A stall watchdog (no activity for 8 s while presenting) re-prompts the model; a false VAD trigger that yields no transcription cannot freeze the lesson. In Q&A, idle prompts lead to a graceful goodbye and a clean pipeline shutdown so the metrics report always prints.

4. Open-ended goal: learning from the agent's own transcripts

Every session is recorded to data/transcripts/<session>.jsonl: student and bot turns (with slide, mode and whether the bot was interrupted), controller actions, pauses, safety blocks, retrieval hits, and the final metrics. python -m tutor.improve turns that history into concrete improvements:

  1. Deterministic analysis (tutor/improve/analyzer.py, unit-tested): question/answer pairs per slide, interruptions, stalls, safety categories, answers that sounded uncertain, per-session cost and duration.
  2. Judging: a model scores each past answer on accuracy, age-appropriateness, concision and staying on topic, and proposes a better answer where a score is low.
  3. Knowledge: the questions students actually asked are grouped into knowledge/learned_faq.md with correct, kid-friendly answers, then ingested into the vector index — so the next class gets grounded answers to the questions this class asked.
  4. Coaching notes: up to eight actionable bullets (e.g. "on slide 4, students often ask what a tsunami is — mention it briefly") are written to data/learned/presenter_guidance.md and appended to the system prompt on the next start.
  5. Regression check: the eval suite runs against the updated prompt, so a learned note that hurts behaviour is caught before it reaches students.

The loop is offline and reviewable: a teacher can read and edit the FAQ and coaching notes before they are used.

5. Status: completed, limitations, next month

What was completed in this submission. All eight goals and the open-ended goal are implemented and committed: deterministic presentation control with Q&A and jump-back, hybrid pause/resume, layered safety, incremental knowledge ingestion with automatic retrieval, a metrics report, JSONL transcripts with an improvement loop, a 115-test deterministic suite, a 10-scenario judge-based eval suite, and a rebuilt frontend that shows lesson state and controls pause. The real Pipecat pipeline is constructed in a test to verify processor order and tool registration.
Current limitations. (1) Development was done without OpenAI API credit, so the end-to-end voice session, the judge evals and the LLM step of the improvement loop have not yet been exercised live; the code paths are unit-tested and the pipeline construction is verified, but live pacing values (slide gap, stall timeout, VAD thresholds) may need tuning against real audio. (2) Return-to-topic quality still depends on the model honouring the state note; the eval suite exists to measure it but has not produced numbers yet. (3) Safety rules are regex-based and will miss paraphrases; the prompt and optional moderation layer cover the gap but are probabilistic. (4) The knowledge base is small and English-only. (5) A single student voice is assumed; several children talking over each other is handled only by VAD, not by speaker identification.
With one additional month. First, run the live pipeline daily against a bank of recorded classroom audio and tune VAD, smart-turn and pacing from measured user→bot latency; wire the evals and the improvement loop into CI so every prompt change is graded before merge. Second, slide visuals: sync an actual slide deck (images and captions) in the UI to the spoken talking points, with per-slide progress and a teacher dashboard for pause, skip and "raise hand" queueing. Third, richer knowledge: ingest PDFs and teacher-uploaded material at runtime, add citation of sources in answers, and evaluate retrieval precision on a labelled question set. Fourth, safety depth: a fine-tuned classifier trained on the transcript corpus to replace regex, a per-class "topics to avoid" list, and an escalation channel that flags safety events to the teacher in real time. Fifth, robustness and cost: reconnect-and-resume on network loss, a smaller model for routine slide narration with gpt-4o reserved for questions, prompt caching, and OpenTelemetry traces (Pipecat supports them) feeding the metrics report.
